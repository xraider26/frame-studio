# Idea-to-production workflow

Production queue is the default Studio workspace. Enter an idea (batch name is optional), choose a built-in or saved recipe, and create episodes, variations or a campaign. Default is five items; supported range is 1–100 independent projects. Optional individual briefs tell the agent how each item differs. This creates planning work, not completed scripts or generated videos.

Connect an agent using the existing MCP setup. Ask it to read `production_queue`, call `claim_queue_task` with a stable request ID, refresh `get_project`, and follow the returned actual `next_action`. The agent supplies planning documents, claims generation with exact prompts/references, uses authorized local/API tools, returns real media, and records actual inspection. It calls `renew_queue_task` before the 15-minute lease expires and `finish_queue_task` after real progress, or reports a concrete blocker. Closed/expired task retries do not advertise an active lease. Agents cannot approve human gates or alter batch spending/retry/concurrency policy.

## Controls and limits

- **Basic / Professional:** independent local preferences for directing, production defaults, generator settings and queue. Basic keeps essential fields plus help, reference/continuity access, validation, quality and budget controls. Optional detail remains mounted so switching modes retains drafts. No mode changes project data or agent behavior.
- **Queue:** real ready/working/output-wait/approval/attention/paused/complete states, known and unknown costs, worker identity/expiry, failures, quality retries, canonical identity version, and links to existing project tools. Priority and pause are explicit human controls. Pausing prevents new claims/provider starts; already-running external work can finish. Blocked worker notes require user resume.
- **Concurrency:** defaults to two active projects per batch, configurable 1–10. Active real generation jobs and active worker leases occupy slots. This is a project limit, not a promise of simultaneous shots or provider throughput.
- **Budgets:** optional batch cap, one unit, evidenced planned image/video costs, existing project attempt/pilot/total limits, and reported actual costs. Atomic claims preserve limits under concurrent agents. Unknown exposure blocks a configured hard cap. Trashed/canceled attempts retain incurred or reserved costs; local cancellation does not prove a refund. Other units are tracked separately rather than added together.
- **Canonical identity:** choose a source project's production bible and actual image references, during creation or through explicit batch sync. Entities and copied reference bindings carry a canonical version. Edit canonical definitions in the source and sync as a human; running API generation blocks sync. Agents may add other entities but cannot silently replace locked ones, including through recipe application. Named visible entities/speakers select relevant canonical references; style references remain global. Actual model compliance still requires media inspection.
- **Quality retries:** off by default, explicitly enabled by the user, bounded 0–10 automatic revisions (default two). A selected take needs actual image/full-clip inspection and a named defect or failed criterion. Evidence is retained and only the affected media/dependencies reopen. Re-recording an old take cannot consume another retry. Exhaustion requires attention; every later claim still passes budget, attempts and approval gates. The app has no built-in visual scorer.
- **Recipe evidence:** saved recipes show actual usage, observed defects and grouped known/unknown costs. Human pilot/production endorsements require matching captured inputs, real selected compatible media and recorded checks/inspection. File hashes, asset IDs, reviews, source revision and human notes are recorded. Production means reviewed selected shot media, not certification of a final edit, delivery or future artistic quality. Existing recipes without evidence remain usable.

The implementation uses the existing local SQLite/media store, FastAPI/MCP and React Studio. Editing and publishing remain external. No LLM, generation provider subscription, worker daemon or paid generation is supplied or activated by this change. A connected authorized agent performs the work; an idle queue does not run itself.

## Verification

Backend: `backend/.venv/Scripts/python.exe -m unittest discover -s backend/tests -v` (run from backend with `-s tests` for imports). Frontend: `npm test` and `npm run build` from frontend. SDK tests use real MCP stdio connected to actual API handlers through an in-process TestClient; media tests use explicitly synthetic actual image/video files.

Full-browser visual verification remains outstanding after the earlier automatic approval review rejected a browser launch with “blocked by policy.” React/JSDOM verifies actual control interactions, modes, drafts and payloads; it does not certify rendered desktop/mobile appearance. No live paid/artistic pilot has been produced by this implementation.
